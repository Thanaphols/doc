3
วิธีดำเนินงาน

ผู้จัดทำพัฒนา Chatshop เป็น 2 ส่วน ได้แก่ แอปพลิเคชันบนสมาร์ตโฟนที่เจ้าหน้าที่ร้านค้าใช้งาน และระบบบริการหลังบ้านที่รับส่งข้อความกับแพลตฟอร์มภายนอก จัดเก็บข้อมูล และประมวลผลแชทบอท บทนี้อธิบายขั้นตอนการดำเนินงานตั้งแต่การวิเคราะห์ปัญหาจนถึงการพัฒนาทั้งสองส่วน โดยมีหัวข้อดังนี้

3.1 กำหนดปัญหาที่เกิดขึ้นกับระบบงาน
ร้านค้าออนไลน์ที่ขายผ่านแชทต้องเปิดแอปพลิเคชันของแต่ละช่องทางแยกกัน เจ้าหน้าที่ต้องสลับหน้าจอไปมาจนพลาดการแจ้งเตือน เมื่อมีหลายคนช่วยกันตอบก็ตอบซ้ำกันหรือตกหล่น คำถามเดิมต้องพิมพ์ตอบซ้ำทุกวัน และการเปิดคำสั่งซื้อยังจดด้วยมือแยกจากแชท ผู้จัดทำจึงพัฒนาระบบหลังบ้านที่รับข้อความจากทุกช่องทางมาเก็บไว้ที่เดียว และพัฒนาแอปพลิเคชันที่แสดงข้อความเหล่านั้นในกล่องข้อความเดียวแบบเรียลไทม์ พร้อม Push Notification แชทบอท และการเปิดคำสั่งซื้อจากหน้าต่างสนทนา

3.2 การวิเคราะห์ระบบ
ผู้จัดทำวิเคราะห์ระบบจากขั้นตอนการทำงานจริงของร้านค้าที่ขายผ่านแชท แล้วสรุปเป็นผู้ใช้งาน ความต้องการด้านการทำงาน และความต้องการด้านคุณภาพของระบบ ดังนี้
3.2.1 ผู้ใช้งานของระบบ แบ่งออกเป็น 3 กลุ่ม ดังนี้
3.2.1.1 เจ้าของร้าน ผู้สมัครใช้งาน เชื่อมต่อช่องทางแชท เชิญสมาชิกเข้าทีม กำหนดบทบาท และตั้งค่าร้านค้าและแชทบอทผ่านแอปพลิเคชัน
3.2.1.2 เจ้าหน้าที่ ได้แก่ ผู้จัดการ แอดมิน และพนักงานตอบแชท ใช้งานได้ตามสิทธิ์ของบทบาท เช่น ตอบแชท เปิดคำสั่งซื้อ หรือดูรายงาน
3.2.1.3 ลูกค้า ผู้ส่งข้อความหาร้านค้าโดยไม่ต้องติดตั้งแอปพลิเคชันของร้าน ผ่านช่องทาง LINE, Facebook Messenger, Instagram หรือ WebChat
3.2.2 Functional Requirements แบ่งตามส่วนของระบบ ดังนี้
3.2.2.1 ส่วนแอปพลิเคชันบนสมาร์ตโฟน
1) ผู้ใช้ต้องสมัครและเข้าสู่ระบบด้วยอีเมล Facebook หรือ Google ได้
2) เจ้าหน้าที่ต้องดูบทสนทนาจากทุกช่องทางในกล่องข้อความเดียว เลือกดูตามช่องทาง เพจ ข้อความที่ยังไม่อ่าน และค้นหาได้
3) เจ้าหน้าที่ต้องตอบข้อความ ส่งรูปภาพ วิดีโอ และไฟล์เอกสาร ใช้ข้อความสำเร็จรูป และตอบกลับโดยอ้างอิงข้อความเดิมได้
4) แอปพลิเคชันต้องแสดงข้อความใหม่ทันทีโดยผู้ใช้ไม่ต้องรีเฟรช และส่ง Push Notification เมื่อไม่ได้เปิดแอปพลิเคชันอยู่
5) เจ้าหน้าที่ต้องมอบหมาย ปักหมุด จัดเก็บ และติดแท็กบทสนทนาได้
6) เจ้าหน้าที่ต้องเปลี่ยนโหมดแชทบอทของแต่ละบทสนทนา ขอคำตอบแนะนำ และดูผลวิเคราะห์บทสนทนาได้
7) เจ้าหน้าที่ต้องจัดการข้อมูลลูกค้าและสินค้า และเปิดคำสั่งซื้อจากหน้าต่างสนทนาได้
8) เจ้าของร้านต้องจัดการทีม ช่องทาง และการตั้งค่าร้านค้าได้
9) ผู้ใช้ต้องดูรายงานภาพรวมการให้บริการได้
3.2.2.2 ส่วนระบบบริการหลังบ้าน
1) ระบบต้องรับข้อความจาก LINE Official Account, Facebook Messenger, Instagram และ WebChat ผ่าน Webhook
2) ระบบต้องส่งข้อความที่เจ้าหน้าที่ตอบกลับออกไปยังแพลตฟอร์มของลูกค้าได้ถูกต้อง
3) ระบบต้องส่งเหตุการณ์ไปยังแอปพลิเคชันแบบเรียลไทม์ และส่งการแจ้งเตือนผ่าน Firebase Cloud Messaging
4) ระบบต้องแจ้งเตือนเจ้าหน้าที่เมื่อมีแชทค้างตอบนานเกินกำหนด
5) ระบบต้องสร้างคำตอบด้วยแชทบอทจากฐานความรู้ของร้าน และโอนให้เจ้าหน้าที่เมื่อตอบไม่ได้
6) ระบบต้องตอบกลับอัตโนมัติตามคีย์เวิร์ดที่ร้านกำหนด
7) ระบบต้องเปิด REST API ให้แอปพลิเคชัน และตรวจสิทธิ์ทุกคำขอ
3.2.3 Non-Functional Requirements เป็นความต้องการด้านคุณภาพของระบบ ดังนี้
3.2.3.1 ด้านประสิทธิภาพ ระบบหลังบ้านต้องตอบกลับ Webhook ได้ทันที แล้วจึงประมวลผลข้อความในคิวงานเบื้องหลัง เพื่อไม่ให้แพลตฟอร์มส่ง Webhook ซ้ำ
3.2.3.2 ด้านความปลอดภัย ระบบต้องตรวจลายเซ็นของ Webhook ทุกครั้ง ยืนยันตัวตนด้วยโทเคนก่อนเรียกใช้ API และแอปพลิเคชันต้องเก็บโทเคนในพื้นที่จัดเก็บที่เข้ารหัส
3.2.3.3 ด้านการแยกข้อมูล ข้อมูลของแต่ละร้านค้าต้องแยกออกจากกัน ผู้ใช้เห็นได้เฉพาะข้อมูลของร้านตนเอง แม้ทุกร้านจะใช้ฐานข้อมูลชุดเดียวกัน
3.2.3.4 ด้านการใช้งาน แอปพลิเคชันต้องแสดงผลการกระทำของผู้ใช้ทันที เช่น การส่งข้อความหรือการมอบหมายงาน และย้อนกลับสถานะเดิมเมื่อเครื่องแม่ข่ายตอบว่าไม่สำเร็จ
3.2.3.5 ด้านความน่าเชื่อถือ ระบบต้องลองส่งงานใหม่เมื่อล้มเหลว ต้องไม่ส่งข้อความเดิมซ้ำให้ลูกค้า และแอปพลิเคชันต้องดึงข้อมูลล่าสุดใหม่ทุกครั้งที่เชื่อมต่อเรียลไทม์กลับมาได้

3.3 การออกแบบระบบ
3.3.1 สถาปัตยกรรมของระบบ แบ่งการทำงานออกเป็น 4 ส่วน ดังรูปที่ 3.2
@fig สถาปัตยกรรมของระบบ Chatshop
จากรูปที่ 3.2 ส่วนประกอบของระบบทำงาน ดังนี้
3.3.1.1 แอปพลิเคชันบนสมาร์ตโฟน พัฒนาด้วย Flutter เรียกข้อมูลผ่าน REST API รับเหตุการณ์ผ่าน WebSocket และรับการแจ้งเตือนผ่าน Firebase Cloud Messaging
3.3.1.2 ระบบบริการหลังบ้าน พัฒนาด้วย Laravel 10 รับ Webhook จากแพลตฟอร์ม ประมวลผลข้อมูลในคิวงาน สร้างคำตอบของแชทบอท และเปิด REST API ให้แอปพลิเคชัน
3.3.1.3 ฐานข้อมูล ใช้ MySQL เก็บข้อมูลเชิงสัมพันธ์ ส่วนบทสนทนา ข้อความ ฐานความรู้ และโทเคนของอุปกรณ์เก็บใน MongoDB
3.3.1.4 บริการภายนอก ได้แก่ LINE Messaging API, Meta Graph API, บริการแบบจำลองภาษา และ Firebase Cloud Messaging
3.3.2 การออกแบบฐานข้อมูล ระบบแบ่งข้อมูลไว้ใน 2 ฐานข้อมูลตามลักษณะของข้อมูล แสดงความสัมพันธ์ดังรูปที่ 3.3
@fig ความสัมพันธ์ของข้อมูลใน MySQL และ MongoDB
จากรูปที่ 3.3 ข้อมูลที่ต้องการความถูกต้องและมีความสัมพันธ์กันชัดเจน เช่น ร้านค้า ทีม สินค้า และคำสั่งซื้อ เก็บใน MySQL ส่วนข้อมูลที่เพิ่มขึ้นตลอดเวลาและมีรูปแบบหลากหลาย เช่น บทสนทนาและข้อความ เก็บใน MongoDB ตารางใน MySQL มีหน้าที่ดังตารางที่ 3.1 และคอลเลกชันใน MongoDB มีหน้าที่ดังตารางที่ 3.2

3.3.2.1 ความสัมพันธ์ระหว่างข้อมูล ร้านค้าหนึ่งแห่งมีสมาชิก บทบาท ธุรกิจ ลูกค้า และแท็กได้หลายรายการ ธุรกิจหนึ่งแห่งมีช่องทาง สินค้า และกฎตอบกลับได้หลายรายการ และมีการตั้งค่าแชทบอท 1 ชุด ลูกค้าหนึ่งรายมีบทสนทนาและคำสั่งซื้อได้หลายรายการ บทสนทนาหนึ่งรายการมีข้อความได้หลายข้อความ ส่วนเอกสารความรู้หนึ่งฉบับแบ่งเป็นส่วนย่อยได้หลายส่วน
3.3.2.2 การเชื่อมข้อมูลข้ามฐานข้อมูล ข้อมูลใน MongoDB อ้างอิงข้อมูลใน MySQL ด้วยรหัส เช่น บทสนทนาอ้างอิงร้านค้า ธุรกิจ และลูกค้า ส่วนคำสั่งซื้อและผู้รับผิดชอบบทสนทนาใน MySQL อ้างอิงบทสนทนาใน MongoDB ระบบหลังบ้านตรวจความถูกต้องของการอ้างอิงเหล่านี้เอง เพราะฐานข้อมูลทั้งสองไม่บังคับความสัมพันธ์ข้ามกัน

จากรูปที่ 3.4 แพลตฟอร์มส่ง Webhook มายังระบบหลังบ้าน ระบบตรวจสอบลายเซ็นแล้วส่งงานเข้าคิว high และตอบกลับแพลตฟอร์มทันที จากนั้นงานในคิวจะบันทึกข้อมูลลูกค้าลง MySQL บันทึกบทสนทนาและข้อความลง MongoDB คัดลอกไฟล์สื่อมาเก็บในระบบ ส่งเหตุการณ์ไปยังแอปพลิเคชันผ่าน Laravel Reverb ส่ง Push Notification ไปยังสมาร์ตโฟนผ่าน Firebase Cloud Messaging และส่งข้อความต่อให้กฎตอบกลับอัตโนมัติและแชทบอท
3.3.4 ขั้นตอนการทำงานของแชทบอท แสดงดังรูปที่ 3.5
@fig ขั้นตอนการสร้างคำตอบของแชทบอท
จากรูปที่ 3.5 ระบบรอ 6 วินาทีเพื่อรวมข้อความที่ลูกค้าส่งติดกัน แล้วค้นคืนส่วนย่อยของเอกสารความรู้ที่เกี่ยวข้อง ประกอบข้อความสั่งงานจากบุคลิกของร้าน ข้อมูลแบรนด์ บทสรุป และข้อความล่าสุด 20 ข้อความ ส่งให้แบบจำลองภาษาสร้างคำตอบ หากแบบจำลองตอบว่าต้องส่งต่อ ระบบจะติดแท็กรอแอดมินและเปลี่ยนเป็นโหมด Manual
3.3.5 ขั้นตอนการรับข้อมูลแบบเรียลไทม์และการแจ้งเตือน แสดงดังรูปที่ 3.6
@fig ขั้นตอนการรับเหตุการณ์และการแจ้งเตือนบนแอปพลิเคชัน
จากรูปที่ 3.6 เมื่อเข้าสู่ระบบ แอปพลิเคชันขออนุญาตแสดงการแจ้งเตือนจากผู้ใช้ ลงทะเบียนโทเคนของอุปกรณ์กับระบบหลังบ้าน และเชื่อมต่อช่องส่วนตัวของร้านค้าผ่าน Laravel Reverb เมื่อได้รับเหตุการณ์ แอปพลิเคชันจะทำงาน ดังนี้
3.3.5.1 MessageReceived เพิ่มข้อความในหน้าต่างสนทนาที่เปิดอยู่ และปรับข้อความล่าสุดกับจำนวนที่ยังไม่อ่านในกล่องข้อความ
3.3.5.2 ConversationUpdated ปรับข้อมูลของบทสนทนา เช่น ผู้รับผิดชอบ แท็ก และโหมดแชทบอท
3.3.5.3 NotificationCreated ดึงรายการแจ้งเตือนใหม่
3.3.5.4 OrderUpdated โหลดคำสั่งซื้อของบทสนทนาและรายการคำสั่งซื้อใหม่
3.3.5.5 SettingsChanged โหลดการตั้งค่าของร้านค้าใหม่
3.3.6 Push Notification หากแอปพลิเคชันไม่ได้เปิดอยู่ ผู้ใช้จะได้รับการแจ้งเตือนจาก Firebase Cloud Messaging เมื่อแตะการแจ้งเตือน แอปพลิเคชันจะเปิดหน้าต่างสนทนานั้น หรือเปิดหน้ารายการคำสั่งซื้อของบทสนทนาเมื่อเป็นการแจ้งชำระเงิน ส่วนขณะเปิดแอปพลิเคชันอยู่ จะแสดงแถบแจ้งเตือนด้านล่างพร้อมปุ่มเปิดบทสนทนา และไม่แสดงเมื่อผู้ใช้อยู่ในบทสนทนานั้นแล้ว

3.4 โครงสร้างแอปพลิเคชันบนสมาร์ตโฟน
ผู้จัดทำแบ่งโค้ดของแอปพลิเคชันเป็น 4 ส่วนตามหน้าที่ ดังรูปที่ 3.7
@fig โครงสร้างโค้ดของแอปพลิเคชัน
จากรูปที่ 3.7 โค้ดแต่ละส่วนทำหน้าที่ ดังนี้
3.4.1 ส่วน core เป็นบริการพื้นฐานที่ทุกหน้าจอใช้ร่วมกัน ประกอบด้วย ส่วนเก็บโทเคนที่ใช้แพ็กเกจ flutter_secure_storage ตัวเรียก REST API ที่แนบโทเคนให้ทุกคำขอและส่งไฟล์แบบ multipart ได้ บริการเรียลไทม์ บริการแจ้งเตือน และ go_router
3.4.2 ส่วน data เป็นแบบจำลองข้อมูล เช่น บทสนทนา ข้อความ และการแจ้งเตือน และ Repository ที่แปลงข้อมูล JSON จากระบบหลังบ้านเป็นแบบจำลองข้อมูลของแอปพลิเคชัน
3.4.3 ส่วน features เป็นหน้าจอและตรรกะของแต่ละโมดูล 13 โมดูล ได้แก่ การยืนยันตัวตน กล่องข้อความ หน้าต่างสนทนา การค้นหา การแจ้งเตือน ลูกค้า สินค้า คำสั่งซื้อ ทีม รายงาน ช่องทาง ข้อมูลผู้ใช้ และการตั้งค่า
3.4.4 ส่วน shared เป็นวิดเจ็ตที่หลายหน้าจอใช้ร่วมกัน เช่น แถบนำทางด้านล่าง และแผ่นฟอร์มที่เลื่อนขึ้นจากด้านล่างของหน้าจอ
3.4.5 การจัดการสถานะและเส้นทางหน้าจอ การจัดการสถานะใช้ Riverpod โดยสถานะการเข้าสู่ระบบเป็น Provider ต้นทาง เมื่อผู้ใช้ออกจากระบบ Provider ของตัวเรียก API บริการเรียลไทม์ และบริการแจ้งเตือนจะยกเลิกการเชื่อมต่อและล้างข้อมูลของผู้ใช้เดิมทั้งหมด การกำหนดเส้นทางแบ่งเป็นหน้าเข้าสู่ระบบ หน้าสมัครใช้งาน และแถบนำทางด้านล่าง 3 แท็บ ได้แก่ กล่องข้อความ การแจ้งเตือน และข้อมูลผู้ใช้ ซึ่งรวมเมนูไปยังหน้าจอจัดการอื่นทั้งหมด หากได้รับรหัส 401 จากระบบหลังบ้าน แอปพลิเคชันจะลบโทเคนและกลับไปหน้าเข้าสู่ระบบทันที

3.5 โครงสร้างระบบบริการหลังบ้าน
ระบบบริการหลังบ้านพัฒนาด้วย Laravel 10 ประกอบด้วยส่วนต่าง ๆ ดังนี้
3.5.1 ส่วนรับและส่งข้อความ ประกอบด้วย ตัวรับ Webhook ของ LINE และ Meta ที่ตรวจลายเซ็นด้วย HMAC-SHA256 และบริการส่งข้อความออกผ่าน LINE Push API และ Meta Graph API เวอร์ชัน 19.0
3.5.2 ส่วนคิวงานและตัวจัดตารางเวลา ใช้ประมวลผล Webhook แชทบอท และการนำเข้าประวัติแชทในเบื้องหลัง และตรวจหาแชทที่ค้างตอบทุก 1 นาที
3.5.3 ส่วนเรียลไทม์และการแจ้งเตือน ใช้ Laravel Reverb เป็นเซิร์ฟเวอร์ WebSocket และส่งการแจ้งเตือนไปยังโทเคนของอุปกรณ์ผ่าน Firebase Cloud Messaging
3.5.4 ส่วนยืนยันตัวตน ใช้ Laravel Sanctum ออกโทเคนให้แอปพลิเคชันหลังเข้าสู่ระบบ และตรวจสอบโทเคนของ Facebook และ Google ที่แอปพลิเคชันส่งมาก่อนออกโทเคนของระบบ
3.5.5 ส่วนจัดการไฟล์สื่อ คัดลอกไฟล์สื่อขาเข้ามาเก็บในระบบ ย่อรูปภาพด้วย PHP GD และย่อวิดีโอด้วย ffmpeg ก่อนจัดเก็บ
3.5.6 ส่วนแชทบอท ประกอบข้อความสั่งงาน ค้นคืนเอกสารความรู้ และเรียกบริการแบบจำลองภาษา ได้แก่ Ollama, Anthropic Claude, Google Gemini และบริการที่รองรับรูปแบบ OpenAI API
3.5.7 ส่วนการติดตั้งระบบ ระบบหลังบ้านติดตั้งบนเครื่องแม่ข่ายที่มี PHP 8.2 ขึ้นไป เว็บเซิร์ฟเวอร์ร่วมกับ PHP-FPM ฐานข้อมูล MySQL และ MongoDB และเปิดใช้ HTTPS เพราะ LINE และ Meta ส่ง Webhook ไปยัง URL ที่เป็น HTTPS เท่านั้น การนำโค้ดขึ้นเครื่องแม่ข่ายใช้ Bitbucket Pipelines เมื่อรวมโค้ดเข้าสาขา release ระบบจะรันชุดทดสอบ ติดตั้งไลบรารีและสร้างไฟล์หน้าเว็บ คัดลอกไฟล์ขึ้นเครื่องแม่ข่ายผ่าน SSH ด้วย rsync โดยไม่เขียนทับไฟล์ตั้งค่า .env และโฟลเดอร์ storage แล้วปรับโครงสร้างฐานข้อมูล สร้างแคชของการตั้งค่าและเส้นทาง และสั่งตัวประมวลผลคิวให้เริ่มใหม่ บนเครื่องแม่ข่ายมีโปรเซสทำงานตลอดเวลา 3 ส่วน ได้แก่ ตัวประมวลผลคิวที่รันคิว high default และ typing โดยมี Supervisor คอยเริ่มใหม่เมื่อหยุดทำงาน เซิร์ฟเวอร์ Laravel Reverb สำหรับ WebSocket และ cron ที่เรียกตัวจัดตารางเวลาของ Laravel ทุก 1 นาที

3.6 การออกแบบ API
ระบบหลังบ้านเปิด REST API ให้แอปพลิเคชันเรียกใช้ประมาณ 99 เส้นทาง แบ่งเป็นหมวดตามหน้าที่ ทุกเส้นทางยกเว้นการสมัครและเข้าสู่ระบบต้องแนบโทเคนที่ได้รับหลังเข้าสู่ระบบ และระบบตรวจสิทธิ์ตามบทบาทของผู้ใช้ก่อนทำงาน ข้อมูลที่รับส่งใช้รูปแบบ JSON หมวดของ API แสดงดังตารางที่ 3.3

3.7 การพัฒนาแอปพลิเคชันบนสมาร์ตโฟน
ผู้จัดทำพัฒนาแอปพลิเคชันเป็น 13 โมดูลตามโครงสร้างในหัวข้อ 3.4 แต่ละโมดูลทำงาน ดังนี้
3.7.1 การเข้าสู่ระบบและสมัครใช้งาน ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน หรือแตะปุ่ม Facebook หรือ Google ซึ่งเปิดหน้าเข้าสู่ระบบของผู้ให้บริการบนสมาร์ตโฟนโดยตรง แอปพลิเคชันส่งข้อมูลไปตรวจสอบที่ระบบหลังบ้าน เมื่อได้รับโทเคนกลับมาจะเก็บไว้ในพื้นที่จัดเก็บที่เข้ารหัสด้วย flutter_secure_storage แล้วเปิดหน้ากล่องข้อความ ผู้ใช้ใหม่สมัครใช้งานพร้อมสร้างร้านค้าได้ในขั้นตอนเดียว โดยแอปพลิเคชันตรวจรูปแบบอีเมลและกำหนดรหัสผ่านอย่างน้อย 8 ตัวอักษร ดังรูปที่ 3.8 และรูปที่ 3.9

3.8 การตั้งค่าแพลตฟอร์มภายนอก
ก่อนใช้งานระบบ ผู้จัดทำต้องสร้างและตั้งค่าบัญชีบนแพลตฟอร์มภายนอก เพื่อให้ระบบหลังบ้านรับส่งข้อความกับ LINE และ Meta ได้ ให้ผู้ใช้เข้าสู่ระบบด้วย Facebook และ Google ได้ และให้ระบบส่ง Push Notification ได้ ทุก URL ที่ลงทะเบียนกับแพลตฟอร์มต้องเป็น HTTPS ที่เข้าถึงได้จากอินเทอร์เน็ต เส้นทางในหัวข้อนี้ เช่น /webhook/meta หมายถึงเส้นทางต่อจากโดเมนของระบบหลังบ้าน มีรายละเอียด ดังนี้
3.8.1 LINE Official Account ร้านค้าแต่ละร้านสร้างบัญชี LINE Official Account ของตนเอง แล้วนำค่าที่ได้มากรอกในแอปพลิเคชัน ตั้งแต่วันที่ 4 กันยายน 2567 LINE ไม่อนุญาตให้สร้างช่องทาง Messaging API จาก LINE Developers Console โดยตรง ต้องสร้างผ่านบัญชี LINE Official Account ก่อน (LY Corporation, n.d.) มีขั้นตอน ดังนี้
3.8.1.1 สร้างบัญชีและเปิดใช้งาน Messaging API สมัครบัญชี LINE Official Account แล้วเปิดใช้งาน Messaging API ใน LINE Official Account Manager ระบบของ LINE จะสร้างช่องทาง Messaging API ให้อัตโนมัติ
3.8.1.2 คัดลอก Channel ID และ Channel Secret เข้าสู่ LINE Developers Console เลือกช่องทางที่สร้างขึ้น แล้วคัดลอก Channel ID และ Channel Secret จากแท็บ Basic settings ดังรูปที่ 3.29

4) นำคีย์แอปพลิเคชันไปกำหนดในระบบ คัดลอก App ID และ App Secret ไปกำหนดในไฟล์ .env ของระบบหลังบ้านที่ตัวแปร FACEBOOK_CLIENT_ID และ FACEBOOK_CLIENT_SECRET และคัดลอก App ID กับ Client Token ไปกำหนดในไฟล์ strings.xml ของโปรเจกต์แอปพลิเคชันบนสมาร์ตโฟน
5) การจัดการโหมดการพัฒนา ขณะแอปอยู่ในโหมดพัฒนา (Development Mode) บัญชี Facebook ที่ใช้ทดสอบต้องถูกเพิ่มเป็นผู้ทดสอบ (Testers) ในเมนู App Roles ก่อน หรือสลับเป็นโหมดเผยแพร่ (Live Mode) หลังกรอก URL นโยบายความเป็นส่วนตัว เพื่อให้ผู้ใช้ทั่วไปสามารถเข้าสู่ระบบได้
3.8.2.2 แอปเชื่อมต่อช่องทาง ผู้จัดทำสร้างแอปประเภท Business แยกต่างหากอีก 1 แอป สำหรับใช้เชื่อมต่อเพจ Facebook, บัญชี Instagram และรับส่งข้อความผ่าน Messenger โดยเฉพาะ เพื่อไม่ให้ปะปนกับแอปเข้าสู่ระบบทั่วไป มีขั้นตอนการตั้งค่า ดังนี้
1) สร้างแอปประเภท Business แล้วเพิ่มผลิตภัณฑ์ Facebook Login for Business และ Messenger เข้าสู่แอปพลิเคชัน
2) ตั้งค่า Valid OAuth Redirect URIs ในเมนู Facebook Login for Business เลือก Settings แล้วระบุ URL สำหรับเชื่อมต่อช่องทาง 3 เส้นทางตามตารางที่ 3.5 เพื่อรองรับการเชื่อมต่อผ่านระบบเว็บและแอปพลิเคชันบนสมาร์ตโฟน ดังรูปที่ 3.34

4) นำคีย์แอปพลิเคชันไปกำหนดในระบบหลังบ้าน คัดลอก App ID, App Secret และ Configuration ID ไปกำหนดในไฟล์ .env ของระบบหลังบ้านที่ตัวแปร FACEBOOK_PAGES_CLIENT_ID, FACEBOOK_PAGES_CLIENT_SECRET และ FACEBOOK_PAGES_CONFIG_ID ตามลำดับ
5) การจัดการสิทธิ์และโหมดการพัฒนา ขณะแอปอยู่ในโหมดพัฒนา สิทธิ์เหล่านี้สามารถใช้ได้เฉพาะบัญชี Facebook ที่มีบทบาทในแอปเท่านั้น หากต้องการเปิดให้ร้านค้าทั่วไปใช้งาน ต้องส่งแอปให้ Meta ตรวจสอบสิทธิ์ (App Review) และผ่านการยืนยันตัวตนธุรกิจ (Business Verification)
3.8.2.3 Webhook ของ Meta ตั้งค่าที่แอปเชื่อมต่อช่องทาง ในเมนู Messenger แล้วเลือก Webhooks มีขั้นตอน ดังนี้
1) กำหนด Callback URL เป็น https://<โดเมนระบบหลังบ้าน>/webhook/meta เพื่อใช้เป็นจุดรับข้อมูลเหตุการณ์ข้อความจาก Meta
2) กำหนด Verify Token เป็นข้อความลับที่ผู้จัดทำกำหนดขึ้นเอง และกำหนดค่าเดียวกันในตัวแปร META_VERIFY_TOKEN ของระบบหลังบ้าน เมื่อกดยืนยัน Meta จะส่งคำขอ GET มาตรวจสอบค่าโทเคนนี้ ดังรูปที่ 3.35
@fig การตั้งค่า Webhook ของ Meta
3) สมัครรับฟิลด์ messages และ messaging_postbacks ของเพจ Facebook และฟิลด์ messages ของบัญชี Instagram เพื่อให้ Meta ส่งข้อมูลเหตุการณ์ข้อความเข้ามายังระบบหลังบ้าน
4) ระบบหลังบ้านใช้ App Secret ของแอปเชื่อมต่อช่องทาง (FACEBOOK_PAGES_CLIENT_SECRET) ในการตรวจสอบลายเซ็น X-Hub-Signature-256 ของทุกคำขอ Webhook ที่ได้รับ เพื่อยืนยันว่าข้อความถูกส่งมาจาก Meta จริง หากกำหนด App Secret ของแอปเข้าสู่ระบบแทน ลายเซ็นจะไม่ตรงกันและระบบจะปฏิเสธคำขอ
3.8.2.4 เชื่อมต่อในแอปพลิเคชัน ร้านค้าเปิดหน้าเชื่อมต่อช่องทางแล้วแตะปุ่มเชื่อมต่อ Facebook หรือ Instagram แอปพลิเคชันเปิดหน้าอนุญาตสิทธิ์ของ Facebook เมื่ออนุญาตแล้ว ระบบหลังบ้านแลกเป็นโทเคนระยะยาว ดึงรายการเพจที่ผู้ใช้เป็นผู้ดูแลมาให้เลือก แล้วบันทึก Page Access Token และสมัครรับ Webhook ให้เพจนั้นอัตโนมัติ บัญชี Instagram ต้องเป็นบัญชีแบบมืออาชีพที่ผูกกับเพจ Facebook เพราะระบบเชื่อมต่อ Instagram ผ่านเพจที่ผูกไว้ หากโทเคนหมดอายุ ระบบจะปิดช่องทางนั้น ดังรูปที่ 3.36
@fig การเลือกเพจที่ต้องการเชื่อมต่อ
3.8.3 Firebase และ Google ผู้จัดทำสร้างโปรเจกต์ Firebase 1 โปรเจกต์ ใช้ทั้งส่ง Push Notification และเข้าสู่ระบบด้วย Google มีขั้นตอน ดังนี้
3.8.3.1 เพิ่มแอปพลิเคชัน Android ด้วยชื่อแพ็กเกจ co.chatshop.chatshop ใส่ SHA-1 ของใบรับรองที่ใช้ลงนามแอปพลิเคชัน แล้วดาวน์โหลดไฟล์ google-services.json ไปไว้ในโปรเจกต์ Flutter ดังรูปที่ 3.37
@fig โปรเจกต์ Firebase และแอปพลิเคชัน Android
3.8.3.2 สร้างคีย์ของบัญชีบริการจาก Project settings แล้วนำไฟล์คีย์ไปไว้ที่ระบบหลังบ้าน เพื่อให้ระบบหลังบ้านส่งการแจ้งเตือนผ่าน Firebase Cloud Messaging ได้
3.8.3.3 ตั้งค่าหน้าขอความยินยอม OAuth ใน Google Cloud Console ของโปรเจกต์เดียวกัน โดยขอสิทธิ์ email และ profile แอปพลิเคชันใช้ Google Sign-In รับโทเคน แล้วส่งให้ระบบหลังบ้านตรวจสอบกับ Google ก่อนออกโทเคนของระบบ
3.8.4 WebChat ไม่ต้องตั้งค่าบนแพลตฟอร์มภายนอก ร้านค้าสร้างช่องทาง WebChat จากแอปพลิเคชัน กำหนดชื่อ ข้อความทักทาย และสีของหน้าต่างแชท แล้วนำโค้ดสคริปต์ที่ระบบสร้างให้ไปติดบนเว็บไซต์ของร้าน ดังรูปที่ 3.38
@fig โค้ดสำหรับติด WebChat บนเว็บไซต์
